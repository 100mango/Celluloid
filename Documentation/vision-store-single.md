## Held-state mechanism

The successful TouchColor mechanism is reused only as a request/hold/full-display-capture/ack pattern. The XCTest case writes a fresh UUID request in its runner temporary directory and holds the real state for at most 120 seconds. The host parses exactly one stdout marker; a second or malformed request fails. It discovers the runner's current data container using supported fixed-device/fixed-bundle `simctl get_app_container`, reads only that UUID's request, validates the exact UI readiness record, and captures once.

The capture callback has a 100-second wall bound including 20-second reserve before each command. Its native commands are bounded individually: app identity lookup 10 seconds, sample container lookup 10 seconds, runner lookup 10 seconds, screenshot 15 seconds, decode/inspect 10 seconds. Encoding happens only after XCTest exits, so it cannot exhaust the held-state budget. The acknowledgement is atomically published only after its full JSON exists, and includes success/failure, UUID, original image SHA-256 and native RGB dimensions. The test must emit exactly one matching acknowledgement and pass exactly once; xcodebuild must exit normally with status zero. A screenshot or one passed test alone cannot qualify a failed invocation.

`vision_store_stream.py` is the existing owned-group capture adapter with a synchronous already-byte-budgeted observer hook, its live guard, and a shared `CaptureStopped` exception import. Its signal, process-group ownership, output cap and cleanup behavior retain the existing bounded stop path. The observer receives the live cancellation/deadline guard, checked before each nested command and immediately before atomic acknowledgement publication. Held callbacks also require the producer to remain running. Unterminated or stderr request markers fail closed; no callback is synthesized after producer exit. Callback failures use that same stop path. Timeout, signal, late/unfinalized exit, output overflow or uncertain descendant exit raises a durable device barrier. No further device command or runner-container acknowledgement is attempted after uncertainty. Only bounded host evidence finalization is still allowed.

## Image and evidence limits

Parent-approved local candidate bounds. This budget approval does not grant push or native activation:

- Original full-display JPEG: at most 16,000,000 bytes, retained unchanged as `capture-original.jpeg`
- Deliverable: at most 3,000,000 bytes
- If original already fits, use that exact original without re-encoding
- Otherwise encode from the original at quality 65, then 45, then 30, stopping at the first fitting derivative
- Every decode/derivative must be exactly 3840 × 2160, eight-bit RGB JPEG, no alpha, orientation 1; no crop, resize, drawing or compositing API is used
- Original bytes and SHA-256 are checked before acknowledgement, again after acknowledgement staging, at every delivery selection, after each encoding, when packing, and at the final upload verdict; a derivative is explicitly labeled lossy and refers back to the original hash
- If the original exceeds its fixed raw bound, the capture fails with a bounded diagnostic; that oversized file is not silently truncated or uploaded. If all three same-size encodes exceed the deliverable bound, fail while retaining the admitted original. No recapture or resize fallback

The parent approved the 16 MB raw / 3 MB deliverable / 24 MB aggregate limits for this local candidate on 2026-10-07. Raw preservation remains distinct from delivery size. The separately reviewed local activation profile uses these same budgets; publication and native execution still require explicit authorization.

The upload list contains exactly 11 fixed paths: report, manifest, original, optional derivative, five bounded logs (build/UI/screenshot/shutdown/delete), uncertainty marker, and icon receipt. Maximum file-cap sum: 23,187,026 bytes, below the 24,000,000-byte aggregate cap. There is no directory glob, raw xcresult, archive, binary or personal container upload. Manifest members include exact bytes and SHA-256, checked against the original checkpoint and derivative receipts. Image replacement after checkpoint, delivery selection, or pack is rejected. Icon-receipt copies use exclusive creation after existing member validation, so a symlink or pre-existing destination cannot be overwritten. Unknown entries, symlinks, oversized members, a second manifest pack, or aggregate overflow fail. Upload runs only after a successful bounded pack and retains evidence for one day.
